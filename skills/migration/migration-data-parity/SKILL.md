# 新旧系统数据口径逆向与对齐（migration-data-parity）

## 目标与边界

目标不是“把新系统数字凑成旧数字”，而是建立可复算的证据链：

**旧页面 → 旧接口 → 权威明细 → 候选口径 → 旧库复算 → 新系统实现 → 多样本回归。**

只在旧线上行为是明确迁移基准时，把旧接口当“预言机”；若旧功能本身已被需求重新定义为错误，先与用户确认新口径，不要盲目复刻。

全程遵守：

- 旧系统与旧库默认只读，优先调用无副作用的 GET 查询；不要为试探接口触达新增、修改、删除、导出或批量任务。
- 凭证、连接串、Cookie、token 和内网地址只从获授权的运行环境临时读取，不写进 skill、测试、补丁、提交文件或最终报告。
- 每次只锁定一个功能口径。先证明“选入哪些记录”，再处理总数、排序、分页和展示格式。

## 0. 固定对照范围与证据表

先选一个最小可复现差异，例如“某年某月少 2 条”，并记录：

| 项目 | 内容 |
|---|---|
| 对照功能 | 同一个旧页面与对应的新页面/接口 |
| 样本矩阵 | 至少 3 个时间点，另加边界月、空月、跨月记录等条件 |
| 对齐主键 | 稳定业务 ID；没有时使用经核验的唯一字段组合 |
| 候选变量 | 类别、状态、发布日期、业务窗口起止、全年有效标记等 |
| 三方结果 | 旧线上明细、旧库按假设复算结果、新系统结果 |

不要一开始只看年度/月度总数。总数只能发现差异，明细成员差异才能反推规则。

## 1. 逆向旧 SPA，找出页面真实接口

### 1.1 从 HTML 到入口包

1. 获取旧页面 HTML，找出入口脚本，常见为 `app.js`、带构建 hash 的入口包或 `runtime.js`。
2. 下载入口包及 webpack runtime；若有 source map 可辅助阅读，但不要依赖线上一定提供 map。
3. 在路由定义中定位目标页面，顺着懒加载 `import()` 找到页面 chunkId。
4. 同时查 webpack 的 chunk URL 构造函数、`publicPath` 和 hash 映射，确认真实文件名模板。

**不要假定文件名一定是 `chunk-<id>.<hash>.js`。** 构建可能定制为：

```text
js/<chunkId>-<buildHash>.js
```

因此应以 runtime 中实际拼接函数为准，而不是按常见命名猜 URL。chunkId、buildHash、静态资源前缀缺一不可。

### 1.2 从页面 chunk 到 URL

1. 在页面 chunk 中搜索请求封装调用，例如 `$http.xxx`、service 方法名或页面查询动作。
2. 回入口包/公共服务包，找“方法名 → 相对 URL”的映射。
3. 找 axios/fetch 实例配置，确认 `baseURL`、公共前缀、请求方法、参数位置和拦截器追加的公共参数。
4. 按以下来源拼真实地址，避免重复或漏掉 `/api`：

```text
站点 origin + axios baseURL + 方法映射 URL + 页面实际查询参数
```

5. 记录参数序列化细节：年月是否补零、日期用时间戳还是字符串、数组如何编码、分页是否从 0 开始、是否必须带特定 Header。

最后得到一张可复核链路表：

| 链路环节 | 证据 |
|---|---|
| 页面路由 | 路由名、路径、chunkId |
| 资源定位 | chunk 文件名模板、hash、publicPath |
| 请求动作 | 页面调用的方法名与实参 |
| URL 映射 | service 方法对应路径与 HTTP method |
| 公共配置 | baseURL、公共参数、必要 Header |
| 最终接口 | 脱敏后的完整 URL 示例 |

若压缩包难以阅读，只做本地格式化或提取字符串；不要把整个旧前端产物复制进新仓库。

## 2. 用旧线上只读接口获取权威基线

优先直接请求旧线上接口，避免旧页面二次加工、缓存或展示截断干扰。以下仅为脱敏示例：

```bash
curl -fsS 'https://legacy.example.invalid/api/sys/api/article/countMonthPolicy?year=YYYY'
curl -fsS 'https://legacy.example.invalid/api/sys/api/article/getPolicyMonth?year=YYYY&month=MM'
```

执行时：

1. 先核对 HTTP 状态、Content-Type 和业务响应码，防止把登录页、网关错误页当 JSON 基线。
2. 同时保存计数与明细；分页接口必须翻完，确认没有默认页大小截断。
3. 明细保留原始关键字段，不要只留标题；排序字段、空值和时区也可能影响判断。
4. 请求需要鉴权时仅使用当前获授权会话，不在命令历史或产物中粘贴凭证。
5. 临时响应放仓库外，验证后删除含敏感数据的文件。

将旧线上去重后的明细 ID 集合记为 `LegacyLive(period)`，它是后续规则复算的主要对照物。

## 3. 用多样本成员变化反推归期与过滤规则

### 3.1 建立明细判定表

把多个时间/条件下“入选与排除”的记录并排列出：

| 业务 ID | 类别/状态 | 发布日期 | 窗口开始 | 窗口结束 | 全年有效 | 对照期 | 旧线上是否入选 |
|---|---|---|---|---|---|---|---|
| 脱敏 ID | ... | ... | ... | ... | ... | ... | 是/否 |

至少覆盖：

- 普通单月记录；
- 起点或终点恰好落在月首/月末的记录；
- 跨月、跨年的记录；
- 全年有效标记为真/假的记录；
- 发布日期与业务窗口落在不同年份的记录；
- 仅类别、状态或删除标记不同的相似记录；
- 空窗口、单边窗口等空值边界。

### 3.2 提出可证伪的候选规则

把自然语言假设写成明确谓词，并逐条对照边界记录。例如月历常见候选包括：

- 按发布日期归月，还是按业务窗口与月份区间相交归月；
- 区间相交是否包含起止当天；
- 跨月记录是否每月出现，全年有效是否特殊放行；
- 是否要求窗口起点或发布日期落在所选年；
- 类别、发布状态、下架状态、删除标记是否参与过滤；
-  NULL/空日期是排除、回退发布日期，还是按另一端点处理。

某次实践最终锁定的是“按窗口实际起止覆盖归月 + 全年受理不特殊放行 + 窗口起点或发布日期须落在所选年”。**这只是案例结论，不是所有月历的默认规则**；必须重新用当前旧系统明细证明。

### 3.3 回旧库按假设复算，锁定集合而非凑数

获得授权后，用只读 SQL 在旧库实现候选谓词。表名和字段按实际库替换，示意如下：

```sql
SELECT business_id, publish_date, window_start, window_end
FROM legacy_content
WHERE <候选类别与状态条件>
  AND <候选归月与年份条件>
ORDER BY business_id;
```

每个假设至少比较：

```text
旧库复算有、旧线上无  → 找出过宽条件对应的记录
旧库复算无、旧线上有  → 找出漏选条件对应的记录
两边都有            → 不应再参与规则猜测，作为正例回归样本
```

使用业务 ID 做集合对称差，不能只比较 `COUNT(*)`。只有多个时间/条件下都逐条吻合，才算锁定主口径；单月吻合很可能只是偶然。

若无法访问旧库，可继续扩大线上样本矩阵并锁定高置信规则，但结论要明确标注“由接口样本归纳，未经旧库 SQL 复算”。

## 4. 识别旧接口自身瑕疵，避免追错方向

旧系统的 count 与 list 可能走不同 SQL，甚至稳定存在固有 1 条差。遇到此类情况：

1. 在多个期间检查差值是否重复出现，比较 count、原始 list 长度和去重后 ID 数。
2. 先以可下钻、可解释的 list 明细锁定主口径，不要为了迎合 count 往明细规则里硬塞一条。
3. 将“主口径差异”和“旧接口计数瑕疵”拆成两个问题记录。
4. 主口径对齐后，再与用户决定是否复刻旧计数缺陷；通常新系统应让计数与明细一致，而不是复制历史 bug。

同理，缓存延迟、分页截断和重复记录也要先排除，避免把接口瑕疵误判为业务过滤规则。

## 5. 按锁定口径修复新系统并补测试

1. 把确认后的规则集中在新系统的一处归期/过滤逻辑中；统计与明细若分别查询，应复用同一谓词或服务，防止再次漂移。
2. 保留“规则文字 + 代表性旧样本 + 代码分支”的对应关系，不复制无关旧实现。
3. 单元测试至少覆盖当前规则的真实分支：
   - 普通入选与明确排除；
   - 月首、月末、跨月、跨年；
   - 全年有效标记不特殊放行（若本案已证实）；
   - 所选年约束；
   - 空日期/单边窗口及类别、状态过滤。
4. 用旧线上已确认的边界 ID 构造匿名测试夹具，不在测试里放真实敏感业务内容。
5. 如测试框架允许，把候选规则写成参数化用例，确保每个反例都能让旧实现失败、新实现通过。

### Maven 验证陷阱

不要只跑 `mvn surefire:test`：直接调用插件目标通常不会自动经过 `test-compile`，修改后的主代码/测试代码可能未重编译，造成“测试过了但跑的是旧 class”。

使用生命周期阶段：

```bash
mvn -pl <module> -DskipTests=false -Dtest=XxxParityTest test
```

`test` 会经过编译与测试编译阶段；若项目默认跳过测试，按项目配置显式打开。多模块是否需要 `-am` 及其无匹配测试策略，按该项目 reactor 配置调整。

## 6. 用三方对照闭环

至少选择 3 个正常期间和全部关键边界样本，输出：

| 期间/条件 | 旧线上明细 | 旧库规则复算 | 新系统明细 | count/list | 结论 |
|---|---:|---:|---:|---|---|
| 样本 A | ID 集合及数量 | 逐条一致/差异 | 逐条一致/差异 | 一致/已知差异 | 通过/待办 |
| 样本 B | ... | ... | ... | ... | ... |

完成标准：

- 旧库复算与旧线上在锁定样本上逐条吻合；
- 新系统与旧线上主明细集合一致，而不只是总数一致；
- 计数与明细关系已解释，历史瑕疵有单独结论；
- 新口径各分支有测试，且测试确实经过重编译；
- 临时响应、SQL 和连接信息未落入提交文件。

## 常见误区

- 只抓浏览器页面上现成的 XHR，可能漏掉封装参数；接口来源不明时才需要完整走 chunk 逆向，已有 Network 证据时可直接复用。
- 猜 webpack 标准文件名而不看 runtime，会在定制构建上反复 404。
- 忘拼或重复拼接 axios `baseURL`，会把接口不存在误判为旧系统无数据。
- 只调一个月份、只看 count，会把偶然吻合当规则。
- 用新库数据反推旧规则，源数据迁移差异会污染结论；规则复算优先回旧库。
- 为最后 1 条差长期改主口径，可能是在复制旧系统 count/list 缺陷。
- 测试只验证新实现自洽，没有旧系统已确认的入选/排除反例，无法证明迁移对齐。

## 最终汇报建议

简明交付四项：**真实旧接口与参数、锁定后的业务谓词、三方逐条对照结果、已实现的代码/测试及仍保留的旧系统瑕疵说明**。若是纯排查未改代码，也要明确“已锁定”与“仅高置信推断”的边界。
