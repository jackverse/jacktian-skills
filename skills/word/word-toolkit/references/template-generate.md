# 专题:按模板批量生成格式一致的文档

把一份既有 Word 模板(公司/行业固定格式)复制为副本,保留其封面、样式、页眉脚、分节,
替换正文与目录为 Markdown 内容,产出与模板格式一致的新 docx,并渲染校验。

## 何时用

- 有固定格式模板,要按新项目内容产出同类文档(验收四件套、方案书、报告……)
- 模板里有封面/修订记录表/目录页/页脚页码,手工复制粘贴容易丢格式
- 一次生成多份、或反复修订重生成

## 脚本

`scripts/` 下以下工具,全部只依赖 `python-docx`(build/analyze)与
`pywin32`、`pypdfium2`、`pillow`(渲染校验):

| 脚本 | 作用 |
|------|------|
| `analyze_docx.py` | 模板版式体检:分节/页边距/页眉脚(含 PAGE 域检测)/样式定义/目录标题/封面段落/修订表结构/媒体与隐藏域计数,可选 `--outline` 输出标题大纲 |
| `build_docx.py` | 核心构建:复制模板 → 全文替换 → 删旧目录旧正文 → 注入 Markdown 正文 → 重建目录域 → 写修订记录 → 清未引用媒体 |
| `build_pipeline.py` | build_docx 构建 + 老模板三暗坑后处理（标题 numPr/TOC 域归位/分节符恢复），用法见脚本 docstring |
| `word2pdf.py` | Word COM 独立实例只读转 PDF,**先更新目录域**(页码才会出现),不动用户已打开的 Word |
| `pdf2png.py` | PDF 渲染 PNG 供视觉检查;`--footers` 提取页脚文字并自动校验页码单调递增 |
| `fill_img_placeholders.py` | `::IMG::` 截图占位框回填真实图片(题注全等匹配),详见 [img-backfill.md](img-backfill.md) |

## 工作流

### 1. 分析模板(先读版式事实,不靠肉眼)

```bash
python scripts/analyze_docx.py 模板.docx --outline --out tpl_report.md
```

重点看:① Heading 样式是否存在且"段前分页"与否;② 有没有 `Table Grid` 表格样式;
③ "目录"标题段落挂什么样式(决定 build 定位);④ 修订记录表(表 0)几行几列、
记录行格式;⑤ 页脚哪几节有 PAGE 域;⑥ document.xml 是否含 fldSimple(隐藏"幽灵目录"域)。

### 2. 写内容 Markdown

build 可识别的方言(**刻意无列表语法**,中文公文用不到):

```
# ~ ######        → Heading 1..6(标题文字不要带编号)
普通段落           → Normal;支持 **加粗**
| a | b |         → 管道表格;首行=表头(表头重复/行不拆分/底纹);单元格内禁用竖线字符
::IMG::说明文字    → 截图占位框(单格边框表 + 居中题注),后续人工贴图
!PAGEBREAK        → 分页
```

- **表格必须写表头分隔行**:表头行后紧跟 `| --- | --- |` 分隔行,漏写则整张表退化为
  以 `|` 开头的普通段落(渲染成竖线文本),内容对账不易发现,视觉校验才看得出来。
- 标题编号默认 **auto 模式**:行首字面编号一律剥离,标题文字不带编号。多数模板的
  Heading 1/2/3 样式自带自动编号(numId 挂在样式上,`lvlText` 如"第%1章"/"%1.%2"/
  "%1.%2.%3"),python-docx 新建的标题段**不带 numPr 覆盖就继承样式编号**,文字里再带
  字面编号会变成"双重编号"。
- 确需 Heading 4+ 时注意:H4+ 样式常挂在**独立 numId**上,与 1-3 级的主编号列表不同步。
  两条路:`--mode manual` 按 manual 模式给 3 级及以下重算字面编号(如 `7.4.1`,按上下文
  而非平铺序号——适用于 1/2 级样式自动、深层级不自动的模板,用户操作手册常见);或给
  H4+ 段落加 numPr 覆盖(ilvl=3、numId=主编号列表)挂回主列表,继续吃自动编号。
- 内容纪律:数字/人名/URL 只能来自用户提供的事实材料,不编造;没有的事实写
  "以实际部署环境为准"。

### 3. 构建

```bash
python scripts/build_docx.py 模板.docx content.md 输出.docx --mode manual \
  --replace "旧项目名称=新项目名称" --replace "二〇二五年五月=二〇二六年十月" \
  --rev-date 2026.10.14 --rev-ver V1.0 --rev-desc 新建 --rev-author 项目组
```

- `--replace` 可多次,替换覆盖**全文**(封面、修订表、页眉脚、域缓存文本)。
  日期若有多种写法(`二〇二五年五月`、`2025年5月`)要逐个传。
- 构建结束打印统计:`body_start / toc paras / rev_row / tables / paras / media dropped / footer_fixed`。

**老模板暗坑**:接手的老模板常埋着 analyze 看不出的雷——包内 NULL 悬空关系
(python-docx 直接打不开)、标题编号靠段落级直接 numPr(注入标题丢编号)、"目录"
标题前藏空 toc 段(TOC 域插到"目录"之前)、分节符挂在旧目录区段落上(删旧目录即
塌节)。老模板构建后务必校验节数、标题编号与目录位置,或直接改用 `build_pipeline.py`
一键构建+后处理;四坑的现象/根因/修法/识别见 [pitfalls.md](pitfalls.md) 第 16-19 条。

### 4. 内容对账(渲染前)

用 python-docx 把产物的标题大纲 + 全文 dump 出来,与 md 源对账:

- 标题一一对应:数量、顺序、文字(编号差异除外——auto 模式已剥离字面编号)。
- 全文 grep 过时术语:旧项目名/旧技术名词/旧日期,产物与 md 源两侧各查一遍。
- 目的:渲染前先确认"产物 = 源 + 预期加工",把"内容不对"定位到构建侧还是源侧
  (疑似不对时的完整排障见下文「证据链」)。

### 5. 渲染校验(必须做,不要目测)

```bash
python scripts/word2pdf.py 输出.docx 预览.pdf        # MS Word COM;无 Word 时降级 LibreOffice
python scripts/pdf2png.py 预览.pdf pages --footers   # 页脚数字单调性脚本判定
```

- **LibreOffice 降级渲染不刷新 TOC 域**(目录页码缺失/停留在旧值),只可作排版粗检;
  交付版必须走 Word COM(先 `TablesOfContents.Update` + `Fields.Update` 再导出,
  word2pdf.py 已内置)。
- 打开生成的 docx 时 Word 会提示"更新域"→ 是,目录页码即刷新(build 已设
  `updateFields`,有的版本仍会问一次)。
- `--footers` 输出每页页脚文字 + 单调性结论,断点直接列出。**勿用肉眼读渲染图上的
  小字号页脚数字**(1.6x 下 40/13 会看成 4/1)。
- 交付前用 zipfile 直读 document.xml 做残留检查:旧项目名/旧日期/旧人名应无命中;
  注意真实业务词(如赛道名)可能合法包含旧关键字,逐条判断。

## 重建优于打补丁(老模板尤其)

接手的老 docx/老模板正文常残留大量与目标项目无关的样板章节(上个年代的过时技术描述:
J2EE/SOA/WebService/ActiveX 之类)与老剪贴画图片。此时:

- **从模板全正文重建,不要在旧 docx 上打补丁**。补丁式修改必漏删残留,逐处排查残留的
  成本远高于一次重建;重建 = build 的"删旧目录旧正文 + 注入 md + 清未引用媒体"全链路。
- 模板旧媒体不必逐张人工找:`strip_unused_media` 用**包内 rels 引用分析**整体剥离——
  遍历包内 `**/*.rels` 建立 rid→media 映射,统计各 part XML 里
  `r:embed/r:id/r:link/r:pict` 的实际引用,全包未引用的 media 直接删并同步清 rels
  悬空项。手工清理照同一思路做,不要按文件名猜。

## 按正式参考 docx 重建规范版式

拿一份正式参考 docx 作"规范样本"重建同版式文档时，版式基准一切从参考文档取，不要凭记忆硬编码；封面/修订表/目录/页眉脚沿用模板复制链路原样保留，正文格式以收割的格式原型为准（见 pitfalls 11）。正式文档的常见基准值（实测为准）：正文宋体/Times New Roman 小四（12pt）、首行缩进约 0.847cm（即两字符）、1.3 倍行距；封面标题大号中文字体（常见 26pt 级）、单位与日期 14pt 居中，封面只换字不重建。

重建时最容易做错的三处：

- **修订记录表列宽要逐 cell 设**：合并行与数据行的每个 cell 都要单独设 `cell.width`（写 tcW）；只设 `column.width` 对已存在的单元格不生效，渲染仍按自动布局走，列宽全乱。表格风格用 Table Grid。
- **页码从正文重启**：封面/目录与正文分节，正文节页码从 1 重新开始（`pgNumType start=1`），封面目录不计页码；构建后校验节数与各节页码设置（分节符被删即塌节，见 pitfalls 19）。
- **表标题用无编号自定义样式**：新建"表题"类自定义样式（居中、加粗、不挂编号列表），不要图省事套 Heading 4——H4 常挂独立编号列表（见 pitfalls 15），会把表标题编进章节号，产生错误编号且污染目录。

长表的 tblHeader 重复表头 + 行 cantSplit 见下文 SQL 小节第 3 步与 pitfalls 24。

## 排障:"文档内容不对"先看证据链

先定位问题层级再动手,不要上来就手改产物 docx——手改在下次重建时必丢:

1. **版本链**:bak 目录多版本 docx 互 diff 大纲(`analyze_docx.py --outline` 输出直接
   diff),先排除"拿错版本/构建产物过时"。
2. **产物 vs 产物**:疑似分叉的两版做正文全文 diff(python-docx 段落 `(style, text)`
   序列,或 zipfile 直读 document.xml),找到从哪一段开始不一样。
3. **产物 vs 源**:产物大纲对 md 源大纲 diff——确认"产物 = 源 + 预期加工"后,
   剩下的差异就是源内容本身的问题。

结论分支:构建产物过时 → 用原参数重新 build;源内容错 → 改 md 再 build。

## 从 SQL 演进链生成数据库设计说明书

输入为初始化基线、按日期或版本交付的增量 SQL、migration 脚本时，先得到**最终有效数据模型**，再生成 Markdown/Word；不要把各文件中的 DDL 原文依次拼接成说明书。通用正文生成、模板复刻和渲染仍沿用上面的工作流。

### 1. 按执行顺序合并最终模型

1. **确定唯一顺序**：基线先执行，后续增量/migration 按项目实际版本号、日期或依赖顺序执行，不以文件修改时间代替执行顺序。给每张表、列、约束保留来源文件与语句序号，便于对账定位。
2. **维护逐语句快照**：有效的 `CREATE TABLE` 建立表、列和约束；后续 `ALTER TABLE ... ADD COLUMN` 合并进该表，`DROP COLUMN` 从当前快照移除。已被后续 `DROP TABLE` 删除的旧表及其列、主键、索引不再进入说明书。不要按表名做跨文件全局去重；若执行历史中允许删后重建，应按顺序以最后一次有效定义为准。
3. **完整解析主键**：同时识别列内联 `PRIMARY KEY`、表级 `PRIMARY KEY (...)` 和 `CONSTRAINT <名称> PRIMARY KEY (...)`。复合主键要保留全部键列及括号内顺序，不能只取第一个字段，也不能因约束前有名称而漏识别。
4. **注释与索引一并收集**：列注释有两种形态——列定义行内 `COMMENT '...'` 与独立的 `COMMENT ON COLUMN 表.列 IS '...'`（不同交付方习惯不同），都要解析并归位到对应列；索引要区分唯一索引（`UNIQUE INDEX/KEY`）与普通索引，保留索引名、列序与唯一性标记，漏一种形态该列/索引就在说明书里消失。
5. **按「库名+表名」两元组去重**：先兼容 schema 前缀与反引号 quoting，再以库名+表名为唯一键。基线刷新版常已并入增量脚本里的建表语句，同库同名按靠后定义合并，避免同一张表在说明书里出现两章；**跨库同名属正常现象，不得跨库合并**，章节按库分段组织。`secure_` 等业务前缀表不要散落各处，按前缀语义归组呈现。
6. **不要按普通逗号硬切 DDL**：字段定义可能含括号、引号、默认值表达式和注释。按顶层逗号切分并处理方言 quoting（反引号/双引号内的逗号不算分隔符），或优先使用对应 SQL 方言 parser；无法可靠解析的语句列入人工复核，不静默猜测。
7. **由同一模型生成所有章节**：表清单、表用途、字段明细、主键和索引均读取最终快照，避免不同章节各自扫 SQL 后口径不一致。输入集未包含的表或语义不明的内容明确标为待确认，不编造。

### 2. 生成后逐单元格对账

行数一致不能证明内容正确；新增列可能覆盖旧值，复合主键也可能只漏一个键列。应由最终模型生成预期矩阵，再用 `python-docx` 回读产物做双向对账：

- 以稳定锚点定位表（如章节号+规范表名），以字段名/约束名等语义键定位行，不依赖封面、修订表造成的物理表格序号，也不只靠行号。
- 对输出涉及的每一列逐格比较，例如列名、类型、可空、默认值、注释、主键顺序、索引定义；空白也作为值比较，统一只做有约定的空白/换行规范化。
- **比对前先 strip**：生成端可能在单元格行尾留下空格，两侧文本先去除行尾空白再比对，避免大片假差异淹没真差异。
- **md 侧解析管道表时，表行之间的空行不要把"当前表指针"清空**——md 渲染允许表格中间夹空行，按行扫描时遇空行只跳过、不切表，否则后半张表被当成新表，表数量与内容双双错位。
- 整体断言兜底：表数量、字段总行数、表名唯一性；唯一性按库分段校验——同库同名即重复（要修），跨库同名属正常。
- 同时检查**缺失、额外、重复、错位**：预期→产物找漏项和错值，产物→预期找旧表、旧列及残留；差异报告带表名、语义行键、列名、期望值、实际值和 SQL 来源。
- 修订 SQL 或生成逻辑后重新生成并重跑全量对账，不能只人工补当前发现的单元格。

### 3. Word 渲染检查表头与孤行

内容对账通过后，用 `word2pdf.py` + `pdf2png.py` 渲染并逐页检查；DOCX 结构检查与视觉检查都要做：

- **跨页表头**：真正的表头行设置 `w:tblHeader`，续页应重复且内容一致；首条数据行不能误设成重复表头。普通数据行设置 `cantSplit`，避免同一字段行被拆到两页。
- **表用途跨页**：表标题、用途说明不应孤悬在页底而字段表从下一页开始。对标题/用途段设置 `keep_with_next`，使其至少与后续表头同页；不要给整张大表一律设置整表不分页，否则长表会产生大面积空白。
- **索引孤行**：索引标题、引导行或“索引”标签不能单独留在页底，索引表头也不应孤行；对相关段落用 `keep_with_next`，索引表续页同样重复真正表头。逐页查看渲染图确认没有裁切、异常空白页或孤行。
